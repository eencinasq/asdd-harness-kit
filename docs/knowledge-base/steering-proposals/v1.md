## Goal

> **A steering file in `asdd-harness-kit` is a JIT-loaded modular rule: frontmatter declares *when* it loads (`inclusion`/`tags`) and *what* it is (`classification`); the body declares *what must be true* (invariants), *what is forbidden* (negative space), *how it is checked* (enforcement), and *what happens on conflict* (escalation). One grammar governs the fleet; a consumer-extensible registry makes the install/stamp/adapter enumerations derivable instead of hand-maintained.**

Bloom-calibrated objective (`blooms.taxonomy.md`): **Analyze** (C4×Conceptual) the fleet against `rule.spec` → **Evaluate** (C5) which spec elements are normative for a JIT-loaded rule and which fleet defects are real vs interpretive → **Create** (C6) the ratified profile + conformance contract + phase plan.

1. **One profile, variants declared** — `kit_steering_rule` (adapted `modular_policy`) with six declared variants; no hybrid/implicit formats.
2. **Registry-backed classification** — every steering `.md` is classified exactly once in a two-block (kit + project) registry; install lists, version stamps, README tables, and runtime adapters become *checked projections*, not silent manifests.
3. **Fleet audited, not rewritten** — the matrix is the migration backlog; Phase 1 changes zero kit files. Live defects (tag starvation, budget FAIL) are recorded and dispositioned, not silently patched.


**Frontmatter (mandatory — the JIT contract):**

```yaml

inclusion: always | auto          # required
```

**D-3 — Tag vocabulary frozen at the current 13.** SoT = `sync-state.mjs:62` `PHASES` + `refactor/lite/review/ui`; documented in `_steering-profile.md`. No new tag values in Phase 1; any vocabulary change requires its own `D-*` + validator update + human sign-off. *EARS:* WHEN a steering file uses a tag outside the vocabulary, validation SHALL `fail` (existing `steering-tags.mjs:45-48`).

**D-4 — Tag-coverage invariant (two finding classes).** (a) **Starvation:** a file's `tags` SHALL cover every phase/mode/role where its gates or duties apply; contract↔binding pairs SHALL have symmetric coverage or documented rationale. (b) **Pseudo-always:** a file whose `tags` ⊇ all 9 `PHASES` SHALL be flagged — reclassify `always` or retag; reclassification to `always` requires a fresh budget decision (`D-5` guardrail). *EARS:* WHEN normative content applies to a phase not in `tags`, the conformance check SHALL report `starvation`; WHEN `tags` cover all phases for an `auto` file, it SHALL report `pseudo-always`. *Recorded:* `G-1` (pseudo-always ×3), `G-2`, `G-3` (starvation); `quality-gates.project.md` pending AR-5.

**D-5 — Budget model.** Per-file 24 KB (`R-004` verbatim). Always-budget: recommend raising the recorded binding `32600`→**34,000** at landing — the binding requires "a decision" (`quality-gates.project.md:51`); this proposal is that recorded decision. **Ordering guardrail (`AR-3`):** the effectively-always tier (files whose `tags` ⊇ all 9 `PHASES`) and active-turn measurement SHALL land in `check-guidance.mjs` **before** any `auto`→`always` reclassification; each reclassification then requires a recorded budget re-decision, never a silent tag edit. *EARS:* WHEN always-loaded bytes exceed the recorded binding, `check-guidance` SHALL `fail`; WHEN pseudo-always files exist, the sensor SHALL report them in a second tier.

**D-6 — Procedural boundary (kit-adapted §5.2).** Declarative gates/invariants stay in steering; pure runbooks (install guides, `npm` setup, how-to sequences — `G-15` instances) extract to skills in Phase 2. `session-loop.md` keeps protocol text under a declared `protocol` section — the protocol IS the rule-guarded lifecycle. `quality-gates.md` splits Phase 2: `QG-*` rule tables stay; tutorial/explanatory content moves — target = cap compliance, not an arbitrary byte goal. *EARS:* WHEN a steering file contains a step-by-step procedure not expressing a state/boundary, the Phase-2 linter SHALL flag it for extraction candidacy.

**D-7 — Bloom `[Cn×Type]` tagging: rejected for steering rule text.** Rules are declarative policies, not instructional procedures; consistent with `skills/v7` D-4 scope (skills/agents only). Recorded — no retrofit.

**D-8 — `.harness/config/steering.registry.json` (new SoT, consumer-extensible).** Schema: two blocks — `kit: [{path, class, inclusion, coverage}]` and `project: [{path, class, inclusion, coverage}]`; `coverage` = `[<phase|mode|role>…] | "always"` — the set of match keys where the file's normative content applies, validated against `tags` (`D-4`). *EARS:* WHEN a steering `.md` exists unregistered in either block, or is registered under two classes, `check-invariants` SHALL `fail`; WHEN a consumer registers a file in `project`, it SHALL satisfy the same grammar — no third track. *(AR-4: consumer steering extends via `project`, never by forking the registry.)*

**D-9 — `templates/` = `artifact_template` registry class.** Outside the rule profile; stays at `.harness/steering/templates/` (install-path stability, `install-into.sh:479`); recorded in the registry `kit` block; Phase-2 template profile covers `steering-proposal.md`'s `id:`/`pattern:` grammar. *EARS:* WHEN a file under `templates/` is linted against rule slots, the linter SHALL skip it by class.

**D-10 — Installer safety.** Phase-2 landing items: `guard_steering_collisions` (symmetric to `guard_skill_collisions`, `install-into.sh:678`) covering portable list + `jev` module + `templates/` tree; install-manifest coverage check via registry. *EARS:* WHEN a same-name unmanaged consumer file collides with a kit steering install, the installer SHALL halt before overwrite.

**D-11 — `steering-tags.mjs` hardening + stated consumer stance (`AR-2`).** Missing frontmatter → `fail` for every non-`_` `.md` under `.harness/steering/` — **in consumers too**: consumer-authored steering is exactly the drift vector this standard governs; the escape path is the `project` registry block (`D-8`), not an exemption. Enforce `classification`; `_`-prefix exempt; `auto`⇒≥1 tag (existing); tag-symmetry warning for `x`/`x.project` pairs. *EARS:* WHEN a non-`_` steering `.md` lacks parseable frontmatter, validation SHALL `fail` (upgrades `:35-38`).

**D-12 — Runtime projections generated.** Phase 2: `generate-runtime-steering` produces `asdd-steering.mdc` and the `AGENTS.md:16` enumeration from the registry (marker-delimited regenerated block, like `skills-index` `:17`); `asdd-steering.mdc:18`-style mandated reads are re-expressed as tag rules (the "Any ASDD work" row is a `D-4` violation to fix, not preserve). Interim: validator drift-check compares adapter enumerations vs registry. *EARS:* WHEN an adapter's file list diverges from the registry, validation SHALL `fail`.

**D-13 — Worked artifact = the profile doc itself.** `_steering-profile.md` (contract-doc class) lands at `.harness/steering/_steering-profile.md` **at ratification** — the first artifact of the standard, carrying grammar, tag vocabulary, budget rules.
