## Pattern

- **Pattern:** LP-a9dc05fe (`escalation:E1-scope-spread`, escape)
- **Occurrences:** 3
- **Slices:** drift-consistency, knowledge-simplify, unified-versioning

Evidence:

- scope touches 3 top-level modules: .harness, docs, scripts
- scope touches 3 top-level modules: .agents, .harness, scripts
- scope touches 2 top-level modules: .harness, scripts

## Root cause

All three slices started lite (the default) and hit E1 on their first `feature_started`, because the scope they planned already spanned two or more top-level modules. E1 was predictable at `init-slice` time from the planned paths, not discovered during the work. The "When to use" guide in `asdd-lite.md` tells the agent to choose full only for a "new user-facing capability spanning modules, cross-cutting, or architectural" work. Harness and tooling changes are none of those, so the agent picks lite, and the sensor then forces an escalation that could have been avoided.

## Change

In `.harness/steering/asdd-lite.md` → "When to use", add after the rule of thumb:

> If the paths you already plan to touch span two or more top-level modules, E1 will fire on the first feature: start with `init-slice.mjs --full`, whatever the kind of work.

Alternative, rejected for now: loosen E1 so that `.harness/`, `scripts/`, and `docs/` count as one module. That would hide real spread in product repos, where those directories rarely change together.

## Success criterion

No `escalation:E1-scope-spread` signal from a slice created after `applied_commit`, across the next 10 sessions. `learn.mjs` tracks the signature; if a new lite slice still hits E1, the proposal becomes `ineffective` and the pattern reopens.

## Rollback

Revert the added paragraph in `asdd-lite.md`. No state or script changes.
