## Root cause

There are two defects in the Learning Gate itself, both verified in the working tree on 2026-11-16.

1. **Feedback loop.** `writeSensorSignal` (`cli/src/harness/learning-lib.mjs:109-118`) records every FAIL line of a failing `asdd check --live`/`verify` run as a signal. It filters only WARN lines (`SKIPPED_WARNS = [/^QG-LEARN-/, /^lite slice "/]`, `learning-lib.mjs:53`). A QG-LEARN-04 FAIL restates an existing open pattern, so the learning sensor counts its own verdict as a new escape. Every slice and every pattern collapses into the single signature `sensor:QG-LEARN-04`, which takes 3 Stop runs to open. That pattern then needs its own proposal, and one open pattern produces a second.
2. **Retroactive blame.** The QG-LEARN-04 check (`cli/src/harness/validators/learning.mjs:60-66`) FAILs for any slice that has a knowledge `phase_completed` session and appears in an open pattern's `slices`. It ignores when the pattern opened.
   - `jev-module` completed Knowledge at `2026-10-28T22:30:47Z` (`.harness/state/slices/jev-module/sessions/036-phase_completed-knowledge.json`). That is weeks before LP-06528643's W47 signals.
   - `skill-eval` completed Knowledge at `2026-11-17T01:24:00Z` (`.../skill-eval/sessions/012-phase_completed-knowledge.json`). LP-2a52ea2c then had 1 occurrence (first seen `00:26:22Z`). Its later occurrences came from other worktrees after the summaries were merged.

   A slice that closed Knowledge correctly can therefore be failed later by signals that it did not produce, or that arrived after it closed.

## Change

Options considered:

| # | Option | Assessment |
|---|--------|------------|
| A | Exclude all `QG-LEARN-*` FAIL lines from signal capture | Simple, but it also drops QG-LEARN-03 (malformed proposal), QG-LEARN-05, and QG-LEARN-10 FAILs. Those are real escapes of proposal authoring, not restatements. |
| B | Dedupe per Stop loop (longer episode window) | It only slows the loop down. Three separate sessions still open the pattern. |
| **C** | **Exclude only QG-LEARN-04 FAIL lines from capture, and make QG-LEARN-04 time-aware** | Fixes both defects and keeps the other learning FAILs as signals. |

**Recommendation: C.**

1. In `learning-lib.mjs`, add a `SKIPPED_FAILS = [/^QG-LEARN-04 /]` filter in `writeSensorSignal`, mirroring `SKIPPED_WARNS`. QG-LEARN-04 is derived from a pattern that is already counted. Its signal is that pattern, not a new one.
2. In `validators/learning.mjs`, FAIL QG-LEARN-04 only when the slice's knowledge `phase_completed` timestamp is at or after the time the pattern reached its threshold. The opening episode time, which `derivePatterns` already has from the episodes, would be exposed as `opened_at`. The slice must also have contributed an episode before that completion. When a pattern opens after a slice closed, the WARN for QG-LEARN-03 still asks for a proposal, and the FAIL moves to the slices that close Knowledge while the pattern is open.

Neither change exempts a DRIFT or other product sensor. Open patterns still WARN (QG-LEARN-03) and still block slices that close Knowledge over them.
